## 2. 表面是什么

一个表面是“某份文档显示在哪里、怎么显示”。它不持有文档的任何文字：文字在文档服务里（T08）。关闭表面只是关闭一个视图，文件不动；没保存的输入由文档服务保存或留作恢复稿。

- 每个文件一个表面。再次打开同一个文件，是把它的表面提到最前。
- 表面的种类由文件名决定：`.md` 是 Markdown，其余文本是纯文本。PDF、图片的阅读表面在 T10。

## 3. 位置规则

位置用的是表面所在容器（画布区域）的坐标，不是屏幕坐标。

- 最小 360 × 240，怎么拖都不会更小；也不会比容器大。
- 标题栏永远够得着：不会高过容器顶部，不会低到标题栏出了容器；水平方向至少有 96 像素留在容器里。
- 容器变小时（比如窗口缩小），所有表面被拉回容器内。
- 新开的表面依次错开，不会正好叠在一起。

## 4. 摆放方式

| 方式 | 行为 |
| --- | --- |
| 浮动 | 用标题栏拖动，用右下角缩放 |
| 停靠左、右 | 占一侧全高，宽度不超过容器的一半 |
| 最大化 | 铺满画布区域 |
| 收起 | 不显示，名字排在底部托盘里，点一下回来 |

“还原”回到之前的位置。记住的是一个位置：停靠着的表面最大化之后还原，回到停靠；再还原，回到浮动时的位置和大小。

双击标题栏在最大化和还原之间切换。

## 5. 不抢画布

- 表面所在的那一层对指针不存在，只有每个框自己接收点击。开着十个文档和一个都不开，画布、面板、提问框都一样够得着。没有覆盖整个应用、需要先关掉的遮罩。
- 只在拖动期间占用指针（标题栏和缩放角），松手即释放。
- 在表面里按的键不会到达画布的快捷键：删除、撤销、R、空格、方向键都不会。
- 在表面里撤销，撤销的是文档，不是画布上的操作。

## 6. 入口

| 从哪里 | 结果 |
| --- | --- |
| 文件树里双击文本文件 | 打开表面，画布不加节点 |
| 文件树里新建文件 | 建好后直接打开表面 |
| 画布上新建文件 | 建好节点，同时打开表面 |
| 文件节点上的铅笔，或双击文件节点 | 打开表面 |

T06 留下的节点内编辑框去掉了：节点是文件在画布上的位置和预览，输入在表面里。

双击不是文本的文件（PDF、图片等）目前仍然是加到画布上，等 T10 的阅读表面。

## 7. 布局按画布记住

每张画布记住自己开着哪些文件、各自在哪、是什么摆放方式。记的是文件身份和位置，不含任何文件内容。重新加载或再次打开这张画布时放回原处；已经不在的文件跳过。离开画布时它的表面全部关闭。

## 9. 没做的和已知限制

- **框里还是纯文本框。** CodeMirror、Markdown 预览、PDF 和图片的阅读表面是 T10。
- **只能从右下角缩放**，四条边不能拖。
- **停靠的宽度不能调。**
- **表面之间不会互相吸附**，也不会避开左侧的文件面板和右侧的节点面板。
- **一个文件只有一个表面。** 文档服务支持多个视图，但现在没有“再开一个视图”的入口。
- **只在 macOS 上验证过。**

## 10. 第二轮审查之后的变化（2026-10-14）

详见 `review-round2-response.md`。和上文不一致的地方以这里为准：

- 在最前面的表面就是接收按键的表面：把表面带到前面的任何动作（包括只按标题栏、拖动、从托盘恢复）都把焦点带进去。
- `openFileSurface` 在画布已经离开时返回 `null`，不建表面；为它打开的文档视图会关掉。恢复布局中途离开画布会停下。
- 关闭表面时如果文档没能保存也没能写成草稿，表面会带着文字回到原位置并提示；因离开画布而关闭时只提示，不在别的画布上打开。
- 表面记录了文件所在的工作区，页面会监听它，所以表面里显示的文件即使不在画布上、也不属于当前文件夹，变化也能跟上。
- 第 1、2、6、9 节里说“框里还是纯文本框”“PDF 和图片的阅读表面在 T10”的地方：T10 已经交付了编辑器和阅读器，见 `editors-and-readers.md`。

## 11. 重新加载后画布上的提问抢走焦点（2026-10-15）

**现象。** 桌面端 `documents open beside the canvas` 这一组大约每 9 到 20 次偶发失败一次，每次落在不同地方：`typeIn` 点击 `.cm-content` 超时；“版本”那条里文件内容不对（`expect(received).toBe(expected)`）。

**怎么查的。** 先构建，再把这一组循环跑 20 次，失败 1 次（第 6 次）。Playwright 的调用日志说点击被 `fixed inset-0 z-[60]` 的遮罩挡住；`error-context.md` 的页面快照里，画布上那个提问框是焦点所在（`[active]`），里面是 `VERSION_TWO_H2 = 2`，遮罩是“模型接口”对话框。也就是说，“版本”那条第一次 `typeIn` 的按键没有进 three.py，进了提问框；其中的 Enter 把问题发了出去，没有可用的模型，于是弹出对话框，第二次点击就被它挡住。按键只进去一部分、或对话框出现得晚一点时，表现为文件内容不对。

**原因在应用。** 临时加了一个探针，记录重新加载后焦点和挂载的先后（8 次重新加载，每次都一样）：

| 加载后 | 发生了什么 |
| --- | --- |
| 约 40ms | 提问节点挂载，输入框的 `autoFocus` 拿到焦点 |
| 约 60–90ms | 四个表面按记住的顺序恢复，最后的 three.py 在最前，拿到焦点 |
| 约 130ms | 提问节点“挂载后 80ms 再聚焦一次”的定时器触发，把焦点从 three.py 拿回提问框 |

测试点进 three.py 如果早于 130ms，焦点随后被拿走；不点也一样，按键进的是提问框。`ThoughtNode` 那段代码的注释说“一个节点只在创建时等一次输入”，实现却是“每次挂载”：随画布加载进来、或被视野裁剪（`onlyRenderVisibleElements`）后重新挂载，都会再要一次焦点。所以不只是测试少等了一会儿：人重新打开应用，看着最前面的文档直接打字，字会进画布上的提问框，按 Enter 就发出去。

**修复。** `src/lib/fresh-nodes.ts` 记住两类节点：画布打开时就在的（画布从存储加载完成时记下），和已经拿过一次焦点的。`ThoughtNode` 只对新建的、等待输入的节点聚焦一次：80ms 定时器和输入框的 `autoFocus` 都受这一条约束。编辑已有问题时的 `autoFocus` 不变。

**测试。**

| 测试 | 修复前 | 修复后 |
| --- | --- | --- |
| e2e：after the page is loaded again the question waiting on the canvas leaves the focus with the document in front | 连续 3 次失败，焦点在 `the canvas`，见 `evidence/surfaces-focus-after-reload-before-fix.txt` | 通过 |
| e2e 第 2 条加了一句：双击画布新建的提问自己拿到焦点 | 通过 | 通过（新建时聚焦没有被改坏） |
| `tests/unit/fresh-nodes.test.ts`：随画布加载的节点不算新；新建的算，拿过焦点之后不再算 | 模块不存在 | 通过 |

`typeIn` 在点击之后多断言一句“编辑器拿到了焦点”。以后再有东西抢焦点，会在这里直接报出来，而不是变成字打到了别处、过几步才失败。

**稳定性。** 新测试会等 500ms，正好让后面的“版本”那条错过原来的竞争窗口，所以只跑整组证明不了竞争已经消失。修复后把新测试排除，让“版本”那条照旧紧跟在重新加载之后，循环 40 次，全部通过（每次 10 条）；再连同新测试循环 20 次，全部通过（每次 11 条）。修复前同样的循环是 20 次失败 1 次。

全量回归（2026-10-15）：单元 584 通过加 6 条预期失败；桌面端 71 条全部通过；网页端 3 条通过；构建和 lint 通过。

**没做的。**

- 表面被打开或恢复时，焦点给了框本身，而不是框里的编辑器：编辑器是在框的布局效果之后才建出来的。从文件树双击打开一个文件后直接打字，字哪儿也不去。这和本节的偶发失败无关（测试总是先点进编辑器），另行处理。（已修，见第 12 节）
- 之前报过一次这一组里的 `toContainText` 失败，修复前后共 80 次循环里没有出现，没法确认它是不是同一个原因。

## 12. 打开或恢复的表面，焦点进框里的编辑器（2026-10-15）

**现象。** 第 11 节“没做的”第一条：从文件树双击打开一个文件，或重新加载后恢复表面，焦点停在最前面那个框本身（`[data-surface]` 那个 div），没进编辑器。不点一下就打字，字哪儿也不去。`SurfaceFrame` 的注释说被打开时焦点会进“它的编辑器”，实际没有做到。

**原因。** 框在布局效果里把焦点给 `typingPlaceIn(el) ?? el`。框和编辑器是同一次提交挂载的，但 CodeMirror 由 `TextEditor` 在 `useEffect` 里建，晚于框的布局效果。框那时找不到 `.cm-content`，只好自己拿着焦点；框的 `onFocus` 只在焦点落到框上的那一刻往里转交，那时编辑器还不存在，之后也没人再交。

**修复。** `TextEditor` 建好编辑器后看一眼：焦点正停在它所在的框本身，就交给编辑器（`view.focus()`）。焦点在框里的别处（比如一个按钮）或在框外，都不动。框的布局效果没改。

**测试。** 修复前的失败输出见 `evidence/surfaces-editor-focus-before-fix.txt`。

| 测试 | 修复前 | 修复后 |
| --- | --- | --- |
| e2e `editors and readers`：a file opened from the tree is typed into straight away, with no click into it first（Markdown 和 Python 各一个，不点击直接打字，字进文件并自动保存） | 失败：at-once.md 没变 | 通过 |
| e2e `documents open beside the canvas` 重新加载那一条：原来只看焦点在 three.py 的框里，现在接着不点击打字，字要进 three.py，再撤销回原样 | 失败：three.py 没变 | 通过 |
| 单元：刚打开的表面，焦点在编辑器的 `contentDOM` 上，按键进文档 | 失败：焦点在框上 | 通过 |
| 单元：恢复布局后，最前面的表面焦点在编辑器上 | 失败：焦点在框上 | 通过 |
| 单元：Markdown 从阅读切回编写，编辑器重新建出来，焦点留在切换按钮上 | 通过 | 通过；临时改成“建好就聚焦”时它失败 |

**没做的。**

- Markdown 从阅读切回编写后，焦点留在切换按钮上，要点一下正文才能打字。这是有意的：编辑器只从它自己的框那里接焦点，不从别处拿。要不要改，另议。
