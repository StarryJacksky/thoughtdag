# 研究工作台：多 AI 基线（T25）

记录日期：2026-10-03。本文是工程计划 T25 的交付物：同一张画布上有多个 AI 任务时，今天的代码实际怎么处理模型、effort、工作目录、审批规则、材料和事件。结论分成三类：已有的行为、已复现的缺口、只在代码里看到但没有测到的风险。

所有结论来自合成夹具和假运行时。本机 PATH 里没有 `codex` 和 `claude`，所以这里没有任何一条是用真实 CLI 验证的。

## 1. 怎么测的

`tests/unit/multi-ai-baseline.test.ts` 通过 store 自己的 `addQuestion` 和 `regenerate` 发起提问，走的是应用真实的提问路径，然后在桌面桥接处记录每次运行实际收到的运行时、模型、effort、工作目录、审批规则、提示词和材料文件。

`tests/host/multi-ai-baseline.test.cjs` 用主进程真实的材料写入函数（`runtime/agents/ops.cjs` 的 `writeMaterials`）和假运行时，记录每一轮开始时 Agent 在磁盘上能读到什么。

三个夹具在 `tests/fixtures/research/`：`two-targets`、`same-runtime-two-targets`、`global-default-changed`。

## 2. 事实表

| 项目 | 今天的行为 | 归类 |
| --- | --- | --- |
| 模型：固定了模型的对话线 | 子节点继承父节点固定的模型；工具栏选别的模型不影响它；工具栏之后再改也不影响它 | 已有 |
| 模型：没有固定模型的对话线 | 每次运行时取工具栏当时选中的模型。工具栏改了之后重跑，会换成新模型 | 已复现缺口 |
| 模型：固定的模型在本机不可用 | 改用别的提供方下同名的模型，没有同名的就改用工具栏的选择；事后弹一条提示，不事先确认 | 风险 |
| 模型：实际使用的模型 | 节点记录请求时的模型（`generatedBy`） | 已有 |
| effort | 全局只有一个值，每次运行在发出时读取它。任务自己不保存 effort，全局值改了之后重跑会用新值 | 已复现缺口 |
| 工作目录 | 属于画布，不属于任务。同一张画布上的任务都在同一个目录里运行 | 已有（是下面材料问题的原因） |
| 提示词 | 每个任务的提示词只含自己连线上的材料和共有材料，不含另一条线的 | 已有 |
| 材料文件：交给每次运行的 | 每次运行只写自己连线上的材料文件 | 已有 |
| 材料文件：磁盘上能读到的 | 都写进同一个目录，从不清理。后运行的任务能读到先前为别的任务写的材料 | 已复现缺口 |
| 原生会话 | 两个同运行时的任务各开各的会话，不合并 | 已有 |
| 长期审批：跨运行时 | 在一个运行时上给过的长期许可不会带给另一个运行时 | 已有 |
| 长期审批：同运行时的不同任务 | 画布上任何节点给过的长期许可，会带给同一运行时的所有任务，包括毫不相干的对话线 | 已复现缺口 |
| 流事件 | 按运行 id 分发。两个运行的事件交错到达时，各自的节点只收到自己的 | 已有 |
| 晚到和无主的事件 | 运行结束后再到的事件、不属于任何运行的事件，都被丢弃，不会写进节点 | 已有 |
| 一个运行结束时 | 另一个运行不受影响，继续保持运行中 | 已有 |

## 3. 已复现的缺口

| 缺口 | 现象 | 代码位置 | 归属任务 |
| --- | --- | --- | --- |
| 不相干的任务继承长期审批 | 一条线上批准过“本次对话内一直允许 `npm test`”，另一条无关的线发起运行时，请求里也带着这条许可 | `agent-runtime.ts:335` | T28 |
| 任务不保存自己的 effort | 任务以 `high` 运行过；全局改成 `low` 后重跑同一任务，用的是 `low` | `agent-runtime.ts:332` | T27 |
| 没固定模型的任务跟着工具栏走 | 任务在 Codex 上运行过；工具栏改成 Claude Code 后重跑，换到了 Claude Code 上 | `streaming.ts:205` | T26 |
| 别的任务的材料留在磁盘上 | 任务 X 的材料写进工作目录后，任务 Y 在同一目录运行时能读到它，虽然它只连给了 X | `ops.cjs:26` | T27、T12 |

第三条在上游是有意的设计（没固定模型就一直跟随工具栏）。它和规划要求的“任务创建后配置固定”不同，所以记为缺口，由 T26 引入明确的执行目标来解决，而不是去改现有逻辑的含义。

最后一条对研究隔离影响最大：光看提示词和交给每次运行的文件，两个任务是隔开的；隔不开的是它们共用的那个目录。

## 4. 只在代码里看到的风险

这几条没有写成测试，原因各自写明。

- **固定模型不可用时换提供方**（`streaming.ts:184` 到 `192`，`use-models.ts:74`）：`reconcileModelId` 本身有测试，证明它会换到别的提供方下的同名模型。但“换了之后只提示不确认”发生在生成流程内部，要在有模型列表的环境里才能触发，这次没有搭。规划 R25 要求向别的提供方发送材料前先确认，归 T26、T30。
- **审批回应的路由**：审批请求带着自己的运行 id，回应按运行 id 送回。假桥接目前不模拟审批请求，所以“两个运行同时要求审批时互不干扰”这次没有测，归 T28。
- **同一原生会话的并发写入**：两个任务要续接同一个会话时会不会同时写，这次没有构造这个场景，归 T28。
- **工作目录的回退规则**（`resolveAgentCwd`）：画布没有指定目录时，会用画布镜像的项目目录，或者应用管理的画布目录。这三种来源都是画布级的，没有任务级的。

## 5. 对后续任务的含义

- T26 引入执行目标时，要把模型、effort 等从“运行时读取全局值”改成“创建时复制、之后固定”。上表里两条缺口的测试到时会自动变成通过。
- T27 给每个运行单独的材料目录后，材料残留的缺口才会关闭。只清空共用目录不够：两个任务并行时会互相清掉对方的文件。
- T28 把长期审批的范围收到任务和运行上。现有的“按运行时前缀过滤”是唯一的一层隔离，它挡得住跨运行时，挡不住同运行时。
- 事件分发这一层今天是对的，T28 不需要重写它，只需要在上面加队列和取消的归属。
