# 研究工作台：文件事务（T04）

## 2. 每个操作怎么做

每个操作都是一次小事务：先把“要做什么”写进日志并刷盘，再动手，记下结果，最后标记完成。

**新建。** 名字由主进程选：`Untitled-001.md`、`Untitled-002.md` 这样递增，导图是 `Mindmap-001.tdmap`。文件以独占方式创建，名字被占就换下一个，所以两个同时发起的新建不会互相覆盖。从 Graph 新建的文件一律放进工作区根目录下的 `Graph Files/`，不管调用方指定了哪个文件夹。JSON、HTML、`.tdmap` 用各自最小的合法内容，其余为空文件。

**读取。** 返回文本和版本，版本是文件字节的 SHA-256。同时报告换行风格（`lf`、`crlf`、`mixed`）和是否带 UTF-8 的字节序标记。不是合法 UTF-8 的文件不会被打开编辑；超过 8 MiB 的文件也不会。

**保存。** 调用方给出它读到的版本。流程是：

1. 读当前内容，版本对不上就返回冲突，不动文件。
2. 在同一目录写临时文件并刷盘，权限和原文件一致。
3. 把即将被替换的旧内容存进恢复区。
4. 再读一次当前内容，仍然对得上才继续，否则删掉临时文件、返回冲突。
5. 用改名把临时文件换上去。

只有第 5 步完成才返回“已保存”。原文件带字节序标记的，保存后仍然带。内容没变就什么都不写。

**移动和改名。** `fileId` 不变，登记里的路径跟着走。目标名字已被占用就拒绝，不覆盖。

**复制。** 得到一个新文件和一个新的 `fileId`。目标名字已被占用就拒绝。

**回收。** 有系统回收站就进系统回收站；没有、或者进回收站失败，就移到工作区自己的恢复区。无论哪种，文件都不会被直接删除。登记记录保留并标为 `missing`，引用它的地方仍然知道它是谁。

## 3. 重复请求和崩溃

**重复请求只做一次。** 每个修改操作都带一个操作 id。同一个 id 再来一次，返回上次的结果，不会再建一个文件、再存一次。这在应用重启之后依然成立，因为结果记在日志里。一个操作 id 只能用于一种操作。

**崩溃之后的对账。** 工作区第一次被使用时，先处理日志里“开始了但没有结束”的操作：

| 崩溃发生在 | 对账结果 |
| --- | --- |
| 新建：文件已写好，还没登记 | 文件保留并补上登记；重试得到的就是这个文件，不会多出一个 |
| 保存：临时文件已写，还没替换 | 删掉临时文件，旧内容原样保留；可以用同一个操作 id 再存一次 |
| 保存：已经替换，还没记完成 | 认定为已保存，更新登记；重试不会被误报成冲突 |
| 移动：已经改名，还没更新登记 | 更新登记里的路径 |
| 回收：文件已移走，还没记完成 | 登记标为 `missing`；因为不知道它去了哪里，收据不声称可恢复 |
| 复制：没复制完 | 不登记这个不完整的文件，也不删它 |

对账只会删除自己留下的临时文件，不删别的。日志里崩溃留下的半行会被跳过，不影响它前面的记录，也不妨碍之后继续追加。

## 4. 导入副本

这是项目所有者为 Space 内容选的路线：Space 直连做不了的情况下，把复制或下载出来的内容当本地文件用。

`importText` 把一段文本存成工作区里的新文件，登记时 `origin` 记为 `import`，并带一个 `importedFrom`：来源种类、导入时间、可选的一句说明（页面标题或链接，由用户自己写）。导入时间由主进程填，界面不能伪造。

存下来之后它就是普通的本地文件，读写移动都一样。契约里没有任何“同步”字段，样例里专门有一条“声称保持同步的副本”被拒绝的用例。同名的第二次导入不会覆盖第一次，而是得到带编号的新名字。

## 5. 没有保证的事

- **别的程序在最后一刻写文件。** 第 4 步检查和第 5 步改名之间，别的程序如果恰好写了这个文件，这里发现不了，那次写入会被覆盖。这个时间窗只有一次改名那么宽。文件系统没有提供跨程序的“比较后交换”，这一点做不到完全。被覆盖的内容如果是在第 3 步之前就存在的，恢复区里有它。
- **目录在检查之后被换成链接。** 路径校验和实际打开之间也有同样的时间差。读取时对最后一级拒绝跟随链接，中间目录被替换的情况挡不住。
- **只支持 UTF-8。** 其他编码的文本只是不打开、不覆盖，没有转码功能。

## 6. 这次没有做的

- **还没有界面。** 这些操作已经通过 IPC 和预加载桥暴露给界面（见第 7 节），但还没有任何界面元素调用它们；文件树和新建菜单是 T06。
- **文件夹只能新建。** 文件夹的移动、改名和回收没有做；这需要批量改写登记里的路径。
- **没有从恢复区恢复的功能。** 旧版本和回收的文件都留着，但还没有“恢复”这个操作，也没有清理策略，恢复区只增不减。
- **没有处理外部改动的监听。** 文件被别的程序改了之后，登记里的版本要等下次读取才更新。这是 T05。
- 只在 macOS 上跑过。
- T04 提交时没有跑网页端到端、冒烟和桌面端到端测试。桌面端到端在接线时补上了，见第 7 节。

## 7. 接线（T04 之后补上）

文件操作和变化事件随后接到了界面一侧：

| 层 | 位置 |
| --- | --- |
| 主进程通道 | `desktop/main.js` 的 `workspace:*`，全部经过调用方校验 |
| 预加载桥 | `window.desktopWorkspace` 上的对应方法 |
| 界面客户端 | `src/lib/workspace/client.ts`：发出前校验请求，收到后校验回答 |
| 变化事件 | `src/lib/workspace/events.ts`：按工作区分发，不符合契约的事件丢弃 |

几个要点：

- 回收走 Electron 的系统回收站；失败时退回工作区自己的恢复区。
- 变化事件只推送给应用自己的页面。窗口显示的不是应用时，什么都不推。
- 窗口回到前台时，对已订阅的工作区做一次重扫，补上后台期间可能漏掉的变化。
- 界面客户端给每个操作生成一个操作 id，回执丢了可以放心重试。

在真实的桌面应用里验证过（`tests/e2e-desktop/workspace-files.spec.ts`）：从 Graph 新建落在 `Graph Files/`；保存落盘并带着操作 id 通知页面；用过期版本再存得到冲突而不是覆盖；别的程序改文件后，页面通过真实的系统监听收到通知；导入的文本成为标了来源的本地文件；移动保持身份；回收的文件进恢复区而不是被删掉；不合契约的请求被拒绝且错误信息里没有路径。

这组测试关掉了系统回收站，免得测试文件进到真实的废纸篓里，所以“进系统回收站”这条路在真实应用里没有跑过，只在主进程测试里用替身验证过。
