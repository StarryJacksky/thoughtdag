# 研究工作台：来源提供方（T31）

记录日期：2026-10-04。本文是工程计划 T31 的交付说明：工作区的“来源”怎么被统一成一组调用，本地文件夹和 Space 各自是怎么接在后面的。

## 1. 为什么要有这一层

规划要求 Space 和本地文件夹对等：能当工作区用，能参与 Graph 的上下文操作。要做到这一点，文件树、Graph 引用、冻结输入这些上层代码就不能写死“这是个磁盘路径”。

所以所有来源都回答同样的五个调用：能做什么（`capabilities`）、列出（`list`）、读取（`read`）、写入（`write`）、新建（`create`）。上层代码只面向这五个调用和来源报告的能力，不问“你是本地还是远端”。

## 2. 文件

| 文件 | 内容 |
| --- | --- |
| `runtime/workspace/providers/local.cjs` | 本地文件夹的提供方 |
| `runtime/workspace/providers/space-blocked.cjs` | Space 的提供方，目前只会回答“被阻断” |
| `runtime/workspace/providers/provider-registry.cjs` | 按工作区的种类找提供方 |
| `shared/workspace/provider-helpers.mjs` | 所有调用方共用的做法，主进程和界面用同一份 |
| `src/lib/workspace/provider-contracts.ts` | 界面一侧的入口 |

## 3. 各部分

**本地提供方不增加任何东西。** 它的每个调用都走工作区服务，路径校验、日志、登记一样不少。它只是把本地文件夹放到那五个调用后面。可写的文件夹除“原生页面编辑”外全部支持；只读的文件夹只支持列出和读取。大文件夹分页列出。

**Space 提供方只回答“被阻断”。** 能力全部是 `unknown`，列出、读取、新建都拒绝并说明原因，写入返回“不支持”。它从不返回空列表：“被阻断”和“文件夹是空的”是两个不同的答案。

**以后换上真的。** 有了经过验证的接口之后，真实的 Space 提供方在登记表里替换掉现在这个，登记表以上的代码不用改。测试里用一个假的提供方演示了这次替换。

**登记表是唯一看“种类”的地方。** 没有登记过的种类直接拒绝，不会落到本地磁盘上。本地提供方也不接受 Space 的工作区记录，不管里面的对象 id 长得多像路径。

## 4. 调用方共用的做法

这几条放在共享模块里，主进程和界面用的是同一份代码：

- **只有 `supported` 才动手。** 能力是 `unknown` 或 `unsupported` 时，写入和新建在这一层就被回绝，来源的写入函数根本不会被调用。
- **页面编辑单独看。** 来源能更新文件，不代表能就地编辑原生页面；后者要看 `pagePatch`。
- **列表读到底，并保留“不完整”。** 按来源自己给的游标一页页读。任何一页说不完整，整个结果就是不完整。空的不完整列表意思是“没能列出来”，不是“这里是空的”。来源重复给出同一个游标会被当成错误，而不是无限读下去。
- **区分两个资源用定位信息的每个字段，不用拼接。** 远端对象的 id 即使长得和本地路径一模一样，也是另一个资源；不同账户下 id 相同的对象也是不同资源。
- **写入要报出它读到的版本。** 来源有自己的版本号就用它，没有（本地文件）就用内容哈希。

## 5. 契约上的调整

| 调整 | 原因 |
| --- | --- |
| 写入结果加了 `error` | 原来只有“回执不明”，没有“确定失败了”。磁盘满这类情况是确定失败 |
| 冲突时的当前版本可以为空 | 目标已经不在了的情况 |
| 保存成功时来源版本可以为空 | 本地文件没有独立于内容的版本号 |

## 6. 旧版本记录

规划的 1.0 版本里，资源记录只有路径，没有定位信息和来源版本。1.0 从未发布过，所以磁盘上不会有真实的 1.0 数据；这里仍然按规划做了迁移：读到 1.0 的登记文件时，给每条记录补上本地定位信息，`fileId` 保持不变，下次有变化时整个文件按 1.1 重写。更新的版本只读不重写，这一点在 T03 已经有了。

## 7. 这次没有做的

- **上层还没有改用提供方。** 文件树、文档服务、冻结输入都还不存在（T06、T08、T11）。它们实现时要通过登记表拿提供方，这一点目前只是约定，还没有代码来验证“没有人绕过去”。
- **本地提供方的写入只支持文本。** 二进制写入返回“不支持”。
- **Space 没有任何真实接入。** 这里测的是“被阻断时的表现”和“替换提供方的机制”，不是 Space 能用。
- 提供方本身没有暴露给界面：界面目前通过工作区服务的通道读写本地文件。等上层开始按来源分发时再决定提供方在哪一侧被调用。
