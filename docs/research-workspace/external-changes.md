# 研究工作台：外部变化与重新关联（T05）

记录日期：2026-10-04。本文是工程计划 T05 的交付说明：别的程序改了、挪了、删了工作区里的文件之后，登记记录怎么跟上，什么时候认定“还是那个文件”，什么时候认定“丢了”。

## 1. 文件

| 文件 | 内容 |
| --- | --- |
| `runtime/workspace/reconcile.cjs` | 对账：让一个文件的登记记录和磁盘一致；全量重扫；显式重连 |
| `runtime/workspace/watch.cjs` | 文件夹监听，只产生“有变化”的信号 |
| `runtime/workspace/index.cjs` | 服务上新增 `subscribeWorkspace`、`reconcile`、`rescanWorkspace`、`relink` |
| `tests/host/reconcile.test.cjs` | 20 条测试，在真实的临时目录上跑 |

契约里新增了 `WorkspaceEvent`：一个已登记的文件在磁盘上变了。

## 2. 认定规则

文件的身份是 `fileId`。磁盘上的设备号和 inode 只在对账的那一刻当证据用，不当身份用。

**文件还在原来的路径上。** 只要这条路径没有被看到过“空着”，那里的文件就是同一份文档，不管它是怎么到那儿的。很多编辑器保存时是写一个新文件再改名盖上去，那不算新文档。内容变了就更新版本并通知。

**文件不在原来的路径上。** 按证据强弱找它去了哪里：

1. 先找文件系统身份相同的文件。同一个磁盘上的改名和移动不改变它，这是最强的证据。
2. 找不到，再找内容完全相同的文件，先按大小筛、再比哈希。跨磁盘移动或者被重新写出来的文件靠这条。
3. 恰好找到一个，就跟过去，`fileId` 不变。
4. 找到不止一个，标为 `ambiguous`，不猜。
5. 一个都找不到，标为 `missing`。

**名字从来不算证据。** 别处有个同名文件，不会被当成丢失的那个。

**空文件不按内容找。** 所有空文件内容都一样，这条证据没有意义。

**路径一旦被看到空过，就不再凭路径认。** 文件被删、对账看到过它不在了，之后同一路径上又出现文件：只有能证明是同一个文件（文件系统身份相同，或者内容相同且非空）才认回来，否则仍然是 `missing`。删掉之后在原地新建一个内容不同的文件，不会继承原来的身份。

**丢失期间不操作。** 状态是 `missing` 或 `ambiguous` 的文件，读取会被拒绝，保存返回冲突，移动、复制、回收也被拒绝。因为它原来的路径上现在可能是另一个文件。

**由人来定。** `relink` 是用户明确指出“丢的那个就是这个”。被指的文件必须存在、在工作区内，并且不是另一个已登记的文件。

## 3. 监听只是信号

文件系统上报的事件会重复、乱序、报错文件名，也可能根本不来。所以不从事件里做任何判断：

- 一连串事件安静下来之后，只触发一次重扫。
- 重扫去读磁盘，结论来自磁盘。
- 应用自己写的东西（`.thoughtdag/` 下的记录、保存用的临时文件）不算信号。
- 也可以直接要求重扫，用来补上没收到的事件。窗口回到前台时应当调用一次。
- 第一个订阅者出现时才开始监听，最后一个离开时停止；关闭工作区也会停止。只关自己开的监听。
- 平台不支持监听整个目录树时，监听不启动，显式重扫照常工作。

**自己的操作和外部变化怎么区分。** 不靠时间，靠内容：应用自己保存之后，登记里的版本已经是新的；随后监听信号触发重扫，看到磁盘和登记一致，就没有新事件。所以不存在“保存后一小段时间内忽略所有事件”这种做法，外部程序在那段时间里的修改不会被漏掉。

订阅者收到的事件带着操作 id：应用自己的操作带着它的 id，外部变化是空。

## 4. 验证过的情形

| 情形 | 结果 |
| --- | --- |
| 外部编辑，监听连报三次 | 只通知一次；之后再来信号不重复通知 |
| 两次重扫、单个文件的对账、读文件，其中两个同时发现同一次外部编辑（2026-10-16 补） | 只通知一次 |
| 登记了但还没读过的文件，第一次被重扫看到（2026-10-16 补） | 记下版本，不通知 |
| 应用自己保存，随后监听报事件 | 只有带操作 id 的那一次通知 |
| 编辑器用“写新文件再改名”的方式保存 | 仍是同一份文档，版本更新 |
| 外部改名、移到别的文件夹 | `fileId` 不变，路径跟过去 |
| 只改大小写的改名 | 路径更新为磁盘上的写法 |
| 中文和带重音符号的文件名 | 和别的文件一样 |
| 原文件没了，别处有同名但内容不同的文件 | `missing`，不跟过去 |
| 原文件没了，另有一个内容相同的新文件 | 跟过去 |
| 原文件没了，有两个内容相同的文件 | `ambiguous`；用户重连后恢复 |
| 空文件没了，有另一个空文件 | `missing` |
| 删除后在原地新建内容不同的文件 | 仍是 `missing`；读和写都被拒绝；用户可以显式重连 |
| 文件被移出工作区再原样移回来 | 认回来 |
| 删除后在原地重新写出相同内容 | 认回来 |
| 重连到另一个已登记的文件、文件夹、工作区之外 | 拒绝 |
| 重启之后 | 跟过去的路径仍然有效 |
| 真实的系统监听 | 外部编辑后收到一次通知 |

## 5. 没有保证的事

- **快到没被看见的删除再新建。** 文件被删又立刻在原地新建，中间没有发生过对账，这里分辨不出它和“编辑器替换式保存”的区别，会当成同一份文档的内容变化。两种情况在磁盘上留下的痕迹是一样的。
- **未变判定依赖修改时间。** 文件系统身份、大小、修改时间都没变时，不重新读内容。修改时间精度低的文件系统上，同一时刻内的等长修改可能要到下次读取或保存时才被发现。保存本身总是读内容比对，不受影响。
- **硬链接。** 同一个文件有两个路径时，原路径没了会跟到剩下的那个。
- **搜索上限。** 找丢失文件时最多看 20000 个条目，超过就不再找，按 `missing` 处理。

## 6. 这次没有做的

- **还没有界面。** 订阅、重扫和重连随后已经接到界面一侧（`src/lib/workspace/events.ts` 和客户端，见 [file-operations.md](file-operations.md) 第 7 节），但还没有界面元素使用它们：没有“文件丢失、请重新关联”的提示，也没有选择候选文件的界面。
- **编辑中的文档遇到外部修改进入冲突状态**，这是界面一侧文档服务的行为，属于 T08。这里只负责把变化报出来。
- 没有文件夹级别的跟踪：文件夹被外部改名时，里面每个已登记的文件各自被找回来，没有“整个文件夹移动了”这个概念。
- 只在 macOS（APFS）上跑过。大小写不敏感和修改时间精度在别的文件系统上的表现没有验证。

## 7. 2026-10-16 补：同一次编辑只通知一次

起因：全量 `npm run test:host` 里“外部编辑只通知一次”这条测试偶尔失败（424/425），单独跑总是通过。修复前的证据见 [evidence/external-changes-announce-once-before-fix.txt](evidence/external-changes-announce-once-before-fix.txt)。查下来是两件事；压力测试里还另外碰到了两条偶发失败，一条是测试的问题，一条是对账的问题。

**测试靠固定等待。** 测试发完监听事件后固定等 80ms，再断言收到一次通知。重扫要读登记、看磁盘、算哈希、写回登记（带 fsync），空闲时几十毫秒，负载下会超过 80ms：同样的设置下测得 p90 87ms，最长 115ms。三份全量并行跑 24 次，这条测试 24 次都在第一个断言上失败（`0 !== 1`）；它是文件里第一个走重扫的测试，最冷，所以总是它。反过来，“之后再来信号不重复通知”“自己保存之后的信号不添新通知”这类断言，在重扫慢的时候会白白通过：检查时重扫还没跑完。

现在的做法：测试自己放一个登记过的标记文件，每次发事件前改它一下。这次事件引起的那次重扫会把它和别的变化一起报出来，听到它就说明那次重扫已经跑完，不管花了多久（最多等 10 秒，超时报错说明是哪一步没来）。断言没有放宽：仍然要求恰好一次，“不再通知”也是在重扫确实跑完之后才检查。

**同一个文件的两次检查同时进行，会把同一次编辑报两次。** 这是真问题，和上面的偶发失败不是一个原因。对账先读登记、再看磁盘、最后写回，中间不和同一文件的其他检查排队。两次重扫重叠（重扫比安静窗口慢，后一阵事件的重扫在前一次还没完时就开始；或者窗口回到前台时的重扫赶上监听触发的重扫）、单个文件的对账赶上重扫、读文件赶上重扫，都会两边读到旧登记、看到新内容、各自写回、各自通知。新加的三条测试修复前每次都失败（10/10）。

修法：对账（包括重扫里对每个文件的检查）和重新关联，都放进文件操作层已有的按文件排队的锁（保存、移动、复制、回收本来就用它）。读文件时“记下新内容并通知”这一步也放进去，进去之后先看登记是不是还和读之前一样：已经被别的检查改过，就是那一方改的，它已经通知过了，这边不写也不通知。于是同一个文件的检查一个接一个，后一个看到的是前一个留下的登记。不同文件之间不互相等。应用自己的保存本来就在这把锁里，现在不会再和对账同时进行；修复前试过 20 次保存和重扫同时进行，没有复现重复通知，所以没有单独为它写测试。

**真实监听那条测试也会偶发失败。** 同一轮压力测试里，“真实的系统监听能注意到外部编辑”失败了 3/24（单份全量跑 30 次里失败 2 次）：5 秒内一条通知都没有。macOS 上递归监听什么时候真正开始上报，Node 不告诉调用方；负载下这个时间超过了测试等的 150ms，在那之前的编辑就再也不会报出来（探针：空闲时 0/20 丢失，负载下 1/30 丢失，丢失之后再改一次就报了）。这不是应用的缺陷，设计上本来就靠显式重扫补没收到的事件。测试改为：没听到就每秒把同一次编辑再做一遍，最多 10 秒；断言不变，仍然是恰好一条 `content` 通知，版本是那次编辑的内容。

**重扫第一次看到一个文件的内容，也报成了“内容变了”。** 修完上面两件事之后再跑压力测试，另一条测试（`folders-and-recovery.test.cjs` 里文件夹移动那条）失败了 1/24：移动之前多了一条旧路径上的 `content` 通知，而文件内容根本没变。这条测试用的是真实监听；最可能的经过是监听报了准备阶段自己写的文件，触发的重扫赶在文件第一次被读之前，登记里的版本还是空的，对账就把“第一次看到内容”当成了变化。读文件那条路径早就遵守“第一次看内容不算变化”（`change-notification.test.cjs` 里有测试），重扫没有。这个问题修复前就有，不是这次的改动带来的，只是这次碰上了。修法：登记里还没有版本时，对账只记下版本，不通知；只改了大小写的改名仍然报 `moved`。新加一条测试，修复前失败。

验证：两处修复之后，三份全量并行跑 8 轮（24 次）全部通过。慢磁盘（`stat`、`lstat`、`realpath`、`open` 各慢 20ms）下整个 reconcile 测试文件通过；同样条件下旧版那条测试在第一个断言上失败。

这次没有查的：导出到文件旁边（`putBeside`）写到一个已登记的文件上时，用的是按路径的锁，不在按文件的锁里，它和重扫同时进行会不会重复通知没有检查。
