## 2. R13-01：创建中断后，新文件沿用旧身份

**做法。** 身份在文件有名字之前就定下来，并记进日志：

- `registry.newFileId()` 生成身份，`intent` 记录它。
- `registry.create({ fileId })` 可以重复调用：这个身份已存在就原样返回，什么也不改。
- 正常提交和恢复共用同一步 `finishCreate`。恢复不再问“这个名字上登记的是谁”，所以占着同名的旧身份不会被当成新文件的；提交时旧身份被标为 `missing`，这是 `create` 原有的行为。

没有把 `register` 简单换成 `create`：报告指出的“登记成功、写 `done` 前中断，重试生成第二个身份”由上面的可重复调用解决，有测试。

**报告列的回归要求，逐项：**

| 要求 | 测试 |
| --- | --- |
| 切点：attempt、发布、created、身份提交（4 个）×旧身份 ready、missing×相同、不同内容 | `cut short at …`，共 16 条 |
| 恢复重复执行、相同幂等键重试 | `restarting again and asking again give the same file`，3 个切点，3 次重启 |
| 外部替换同名文件 | `another program puts other content at the name`：回执的 revision 是磁盘上的内容；`another program puts a file at the name that was being tried`：不是这次创建的文件，新文件取下一个名字 |
| 文件在重启前消失 | `the file is gone before the restart`：什么也不认领，重试时重新创建 |
| 新旧 fileId 分离、旧保存 conflict、回执 revision 与字节一致、读取指向新文件 | `oneNewFile` 里的断言，每条都查 |
| 真实临时目录的重启 | 全部用真实临时目录；重启是在同一目录上新建服务实例 |

切点“done 之后”是正常完成的路径，没有单列切点；已有的幂等测试覆盖它。

**报告之外一并修的：**

- **不重启、同一幂等键重试。** 登记表存不下、或 `done` 写不进去时，重试原来会再走一遍创建，得到第二个文件 `fresh-2.md`。现在重试先把上次留下的那一次做完。两条测试。
- **发布后被外部替换。** 恢复原来用日志里写的 revision，现在按磁盘上的字节算。
- **暂时的读取失败。** 恢复时遇到 `EIO`、`EBUSY` 等，操作留到下次，不当作文件不存在。没有专门的测试。

**旧版本留下的日志。** 日志没有身份时，只认“登记表里同名、且 `dev` 和 `ino` 与磁盘文件相同”的记录是它自己的，否则新建身份。两条测试。文件系统复用 inode 时，这一步可能认错：旧文件已删、新临时文件拿到同一个 inode。只影响升级时恰好有未完成创建的旧日志，新日志不走这条路。

**边界，没有做：**

- 没有真实杀进程或断电；`fsync` 之后数据是否真的落盘不在测试范围内。
- 没有验证 Windows、同步卷；没有验证真实的文件监听和画布上的双视图。
- `finishCreate` 找到的身份如果已被标为 `missing`，文件又回到了原名，它原样返回，等下一次对账恢复。没有测试。
- `copyFile` 的恢复路径没有改：未完成的复制本来就不登记。

## 3. R13-02：内置 Agent 能被自动重放

**这一项在 R12 回应里列为“需要决定”。** 我按工程计划已有的规则定了：会写文件的 Agent 不由自动运行启动。内置 Agent 带着画布的工作目录和权限运行，所以算会写文件。行为变化见第 5 节。

**做法。** 只留一个判断：

- `actsAsAgent(modelId)` 回答“这个模型会不会落到一个在文件夹里用工具干活的 Agent 上”，三类运行时和内置 Agent 都算。
- `kindOf(target)` 按模型回答目标是什么。旧记录写着 `provider` 但模型是内置 Agent 的，也算 Agent。
- 新建目标时，`templateFor` 把内置 Agent 记为 `kind: 'agent'`、`runtime: null`；它没有 effort，和原来一样。
- `writesFiles`、`checkSend`、发送前的记录改写、运行信封、运行预览都走这两个函数。信封因此写明它可以写工作目录，研究隔离模式下被挡住，因为没有验证过的能力。
- 界面显示为 `Agent · <型号>`，不再写成 `· API`。

**报告列的回归要求，逐项：** 裸名和带型号各一遍，都覆盖未绑定、固定型号、固定型号不可用时回退到工具栏、服务器默认、已绑定、旧的 Provider 记录、准备期间切换；自动重跑、上游完成触发、受控重放都不派发，也不写任何东西；人工运行和 `mayWrite` 有对照。

**一处差点出错。** 第一版把名字判断放进 `agent-runtime.ts`，让 `dsh-bridge.ts` 从那里导入，造成循环依赖，打包后的页面一加载就报 `Cannot access 'ig' before initialization`，整页空白。单元测试和网页端到端测试都不打包，查不出来；桌面端测试跑构建产物，查出来了。名字判断现在放在不依赖任何模块的 `harness-agent.ts`，并在文件头写明原因。

**边界，没有做：**

- 真实内置 Agent 的工具写入和权限没有验证。这里只证明入口被拦住。
- 在研究隔离模式下，内置 Agent 的运行因能力未验证被拒绝；这是按“未知就拒绝”推出来的，没有真实运行过。
- 模型服务返回的型号名以 `harness/agent` 开头才算内置 Agent，这是现有的命名约定，没有另加能力探测。

## 4. R13-03：Pi 首条纯图片被证明为“无图片”

**做法。** 只有图片或未知内容、没有文字的输入：

- 有问题还在等回答时，它属于那个问题，它的 id 也记进那一轮。
- 否则它自成一轮，后面的回答、工具都归这一轮。
- 紧接着来了文字、中间没有回答，它们合成一个问题。
- 会话停在这里、没有回答，不生成节点，但把标记记到前一轮：原生会话里确实有这张图，不能说前面的历史“无图”。

卡片上的问题显示为 `(image-only turn)`；未知内容显示为 `(input without words)`。不再显示 `(tool-only turn)`。
